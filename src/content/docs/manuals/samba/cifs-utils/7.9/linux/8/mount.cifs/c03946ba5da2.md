## mount\.cifs, mount\.smb3 {#mount-cifs--mount-smb3}


### Common Internet File System（CIFS）を使ってマウントする {#mount-using-the-Common-Internet-File-System--CIFS}


<dl><dt>マニュアルのセクション:</dt><dd><p>8</p></dd></dl>

#### 書式 {#SYNOPSIS}


<blockquote><p>mount.cifs {service} {mount-point} [<code>-o</code> options]</p></blockquote>

<p>このツールは cifs-utils スイートの一部です。</p>

<p>mount.cifs は Linux から CIFS または SMB3 ファイルシステムをマウントします。通常は &quot;<code>-t</code> cifs&quot; オプションを使った mount(8) コマンドから間接的に呼び出されます。このコマンドは Linux でのみ動作し、カーネルが cifs ファイルシステムをサポートしている必要があります。SMB3 は CIFS（SMB）プロトコルの後継で、ほとんどの Windows サーバー、Azure（クラウドストレージ）、Mac、多くの商用サーバーやネットワーク接続ストレージ装置、広く使われるオープンソースサーバー Samba が対応しています。</p>

<p>mount.smb3 は SMB3 ファイルシステムだけをマウントします。通常は &quot;<code>-t</code> smb3&quot; オプションを使った mount(8) コマンドから間接的に呼び出されます。smb3 ファイルシステムタイプはカーネル4.18以降に追加されました。ファイルシステムタイプを smb3 として渡す点を除き、mount.cifs と同様に動作します。</p>

<p>mount.cifs は、service に指定した UNC 名（公開されたネットワークリソース）をローカルディレクトリ mount-point に接続します。UNC 名には //server/share 形式を使い、server はサーバー名または IP アドレス、share は共有名です。</p>

<p>mount.cifs のオプションは、key=value の組をカンマで区切った一覧で指定します。cifs ファイルシステムのカーネルモジュール（cifs.ko）がサポートしていれば、ここにないオプションも渡せます。cifs VFS カーネルコードへ渡した不明な cifs マウントオプションは、カーネルログに記録されます。</p>

<p>mount.cifs により cifs VFS は cifsd というスレッドを起動します。マウント後、このスレッドはリソースをアンマウントするまで（通常は umount ユーティリティーで）動作し続けます。</p>

<p>mount.cifs <code>-V</code> コマンドは、cifs マウントヘルパーのバージョンを表示します。</p>

<p>modinfo cifs コマンドは、cifs モジュールのバージョンを表示します。</p>

#### サービスの形式と区切り文字 {#SERVICE-FORMATTING-AND-DELIMITERS}


<p>サービス名の区切りには通常、スラッシュ（/）を推奨します。Windows マシンでは一般にパス要素内に含められず、クライアントが無条件にバックスラッシュ（\）へ変換できるため、「共通の区切り文字」とみなされます。一方、POSIX はパス要素内のバックスラッシュを許可するため、同様の自動変換はできません。</p>

<p>mount.cifs は可能な箇所でバックスラッシュをスラッシュへ変換しようとしますが、共有名より後のパス要素では変換できません。</p>

#### inode 番号 {#INODE-NUMBERS}


<p>Unix 拡張が有効な場合、POSIX 呼び出しへの応答としてサーバーが提供する実際の inode 番号を使います。</p>

<p>Unix 拡張が無効で serverino マウントオプションが有効な場合、サーバーの inode 番号を取得する方法はありません。クライアントは通常、サーバーが割り当てた UniqueID を inode 番号へ対応付けます。</p>

<p>UniqueID はサーバーの inode 番号とは別の値です。サーバー全体で一意で、しばしば2の32乗を超えます。格納先構造体のフィールドに収まらないため、LFS（Large File Support）を有効にせずコンパイルしたプログラムでは glibc の EOVERFLOW エラーが起きることがあります。防止のため、LFS 対応（すなわち <code>-D_FILE_OFFSET_BITS</code>=64）でコンパイルすることを強く推奨します。noserverino を使えばクライアントで2の32乗未満の inode 番号を生成できますが、ハードリンクを正しく検出できない場合があります。</p>

#### キャッシュの一貫性 {#CACHE-COHERENCY}


<p>CIFS や NFS のようなネットワークファイルシステムでは、他のクライアントやサーバーの操作により、気付かないうちにファイルの内容や属性が変わる問題に対処する必要があります。すべてのファイルアクセスをサーバーへ直接送る方法もありますが、性能面で現実的でないため、多くのプロトコルにはローカルにデータをキャッシュする仕組みがあります。</p>

<p>CIFS プロトコルは実質的に、クライアントが opportunistic lock（oplock）またはリースを持たない限り、ファイルデータをキャッシュしないよう要求します。どちらも特定の種類の排他的アクセスを保証し、サーバーと絶えずやり取りせず内容へアクセスできるようにします。取り消す必要が生じるとサーバーがクライアントに通知し、キャッシュ済みデータをフラッシュするための一定時間を与えます。</p>

<p>CIFS クライアントは、カーネルのページキャッシュでファイルデータをキャッシュします。ページキャッシュを通じた I/O は通常ページ境界に揃えられます。Windows のロックは強制的で読み書きを阻止できるため、バイト範囲ロックとの組み合わせで問題になる場合があります。</p>

<p>cache=none では、通常の読み書きにキャッシュを一切使いません。要求を満たすため、常にサーバーへ直接アクセスします。</p>

<p>cache=strict では、CIFS/SMB2 プロトコルへ厳密に従おうとします。すなわち、oplock を持つ場合だけキャッシュを信頼します。持たない場合はキャッシュを迂回し、サーバーへ直接アクセスして読み書き要求を満たします。これによりバイト範囲ロックの問題を避けます。また、oplock を持つ場合はバイト範囲ロックをクライアントにキャッシュし、その oplock が取り消されるとサーバーへ送ります。</p>

<p>cache=loose はより緩やかなプロトコル動作を許可し、一貫性を犠牲にして性能を向上させる場合があります。ファイルアクセスは常にページキャッシュを介します。oplock またはリースを持たない場合、ファイル書き込みの直後にキャッシュをフラッシュしようとします。ただし、write システムコールが戻る前にフラッシュするとは限りません。</p>

<p>oplock を持たずに読み取る場合、ファイルの変更やキャッシュの無効化を確認するため、定期的に属性を調べようとします。NFSv2/3 のキャッシュ一貫性の仕組みに似ていますが、CIFS では特に問題があります。Windows は、確認に使う LastWriteTime フィールドの更新をかなり遅らせます。このため、複数の読み手と書き手が同じファイルを扱うと、cache=loose によってデータが破損する場合があります。</p>

<p>そのため、複数のクライアントが同じファイル群にアクセスする場合は cache=strict を推奨します。CIFS/SMB2 プロトコルにより厳密に従い、一貫性の問題を解消するのに役立ちます。</p>

<p>どのキャッシュモデルでも、mmap されたファイルは常にページキャッシュで処理します。mmap されたファイルへの書き込みがサーバーにフラッシュされることを保証するのは、msync() 呼び出し時または close() 時だけです。</p>

<p>3.7より前のカーネルでは既定値は loose でした。3.7以降は strict です。</p>

#### CIFS/NTFS ACL、SID/UID/GID の対応付け、セキュリティー記述子 {#CIFS-NTFS-ACL--SID-UID-GID-MAPPING--SECURITY-DESCRIPTORS}


<p>このオプションは、ユーザー認証モデルとして UID、GID、ファイルアクセス権ビット、POSIX ACL の代わりに、セキュリティー記述子と CIFS/NTFS ACL を持つファイルオブジェクトを扱うためのものです。CIFS サーバーで最も一般的な認証モデルで、Windows も使用しています。</p>

<p>対応するには、CONFIG_CIFS_XATTR と CONFIG_CIFS_ACL の両方を有効にして cifs カーネルモジュールをビルドする必要があります。Linux 5.3以降は CIFS/NTFS ACL 対応が常に組み込まれるため、CONFIG_CIFS_ACL は存在しません。</p>

<p>多くのディストリビューションのカーネルでは既定で有効ですが、次の方法で確認できます。</p>

<pre><code>cat /lib/modules/$(uname -r)/build/.config</code></pre>

<p>または、CONFIG_IKCONFIG_PROC を有効にしたカーネルでは:</p>

<pre><code>zcat /proc/config.gz</code></pre>

<p>CIFS/NTFS ACL は、次の Microsoft TechNet 文書に示されたアルゴリズムでファイルアクセス権ビットへ対応付けます。</p>

<p><a href="http://technet.microsoft.com/en-us/library/bb463216.aspx">http://technet.microsoft.com/en-us/library/bb463216.aspx</a></p>

<p>SID と UID/GID を相互に対応付けるには、次のものが必要です。</p>

<ul><li><p>request-key.conf(5) で設定した、カーネルから cifs.idmap ユーティリティーへの upcall</p></li><li><p>nsswitch.conf(5) で設定した winbind または sssd のサポート</p></li></ul>

<p>詳細は cifs.idmap(8)、winbindd(8)、sssd(8) の各マニュアルを参照してください。</p>

<p>ファイルオブジェクトのセキュリティー記述子は、system.cifs_acl という拡張属性で直接取得・設定できます。このインターフェースで渡すものは生のデータ塊なので、解析と整形には getcifsacl(1)、組み立てには setcifsacl(1) のようなユーザー空間ユーティリティーが必要です。</p>

<p>このマウントオプションを使う際の留意事項:</p>

<ul><li><p>セキュリティー記述子の取得・設定のための追加要求により、メタデータ処理の遅延が増える場合があります。</p></li><li><p>CIFS/NTFS ACL と POSIX ファイルアクセス権ビットの対応付けは完全ではなく、変換時に一部の ACL 情報が失われる場合があります。</p></li><li><p>cifs.idmap への upcall が正しく設定されていないか、winbind または sssd が設定・起動されていない場合、ID 対応付けは失敗します。その場合、uid/gid は共有の値、または指定されていれば uid/gid マウントオプションの値になります。</p></li></ul>

#### バックアップ目的でのファイルアクセス {#ACCESSING-FILES-WITH-BACKUP-INTENT}


<p>サーバー上のユーザーがファイルに要求するアクセスは、通常、そのファイルの所有者と ACL に関連付けられた権限で決まります。アクセス権を持たなくても、特別な権利を与えることで、特定の目的のためにアクセスできる場合があります。その一つが、バックアップまたは復元を意図したアクセス（バックアップ目的）です。この権利は通常、組み込みの <em>Backup Operators</em> グループへユーザーを追加して与えます。このユーザーがバックアップ目的でファイルを開こうとすると、CreateOptions の1つとして FILE_OPEN_FOR_BACKUP_INTENT ビットを設定してオープン要求を送ります。</p>

<p>たとえば Windows サーバー上で、<em>testuser</em> というユーザーは、次のセキュリティー記述子を持つファイルを開けません。</p>

<pre><code>REVISION:0x1
CONTROL:0x9404
OWNER:Administrator
GROUP:Domain Users
ACL:Administrator:ALLOWED/0x0/FULL</code></pre>

<p>ただし <em>testuser</em> が <em>Backup Operators</em> グループに入れば、バックアップ目的でファイルを開けます。</p>

<p>サーバーでこのようなユーザーとして認証できるクライアント側のユーザーは、誰でもバックアップ目的でアクセスできます。ただし、安全面をはじめ多くの理由から、この特別な権利を制限する方が望ましいです。</p>

<p>backupuid マウントオプションは、名前またはIDで指定したユーザーだけに、この特別な権利を制限します。backupgid は、名前またはIDで指定したグループのユーザーだけに制限します。backupuid または backupgid のどちらかに一致するユーザーだけが、バックアップ目的でファイルへアクセスしようとします。この2つのオプションは併用できます。</p>

#### ファイルとディレクトリの所有者とアクセス権 {#FILE-AND-DIRECTORY-OWNERSHIP-AND-PERMISSIONS}


<p>基本的な CIFS プロトコルは、ファイルやディレクトリの Unix 所有者情報やモードを提供しません。このため、通常は uid= や gid= オプションの値が所有者として見え、マウントの既定 file_mode と dir_mode がアクセス権になります。chmod/chown で変更しようとすると成功を返しますが、効果はありません。</p>

<p>クライアントとサーバーが Unix 拡張の使用に合意すると、サーバーが提供する UID、GID、モードをファイルとディレクトリに割り当てます。CIFS マウントは通常単一ユーザー用で、誰がアクセスしても同じ資格情報を使うため、新規ファイルとディレクトリの所有者は通常、マウントに使った資格情報に対応します。</p>

<p>クライアントとサーバーで UID/GID が一致しない場合、forceuid と forcegid が役立つことがあります。ただし、モードを上書きする同様のオプションはありません。forceuid や forcegid が有効な場合に表示されるファイルのアクセス権は、実際の権限を反映しない場合があります。</p>

<p>Unix 拡張の使用が合意されていなくても、dynperm マウントオプションでサーバー上のローカルな動作として模倣できます。有効にすると、新規ファイルとディレクトリは適切に見えるアクセス権を受け取ります。ただしサーバーには保存されず、カーネルが inode キャッシュを排出するタイミングによって、いつでも消える可能性があります。一般に、このマウントオプションは推奨しません。</p>

<p>noperm により、クライアントのアクセス権検査を完全に無効にすることもできます。サーバー側の検査は無効にできません。サーバーの検査は常にマウントに使った資格情報に対応し、アクセスしているユーザーとは限りません。</p>

#### 環境変数 {#ENVIRONMENT-VARIABLES}


<p>USER 変数には、サーバー認証に使うユーザー名を設定できます。username<code>%p</code>assword 形式で、ユーザー名とパスワードの両方を設定できます。</p>

<p>PASSWD と PASSWD2 変数には、それぞれクライアント利用者のパスワードと代替パスワードを設定できます。</p>

<p>PASSWD_FILE と PASSWD2_FILE 変数には、それぞれ password または password2 を読み取るファイルのパス名を設定できます。各ファイルから1行を読み、パスワードに使います。</p>

#### 注記 {#NOTES}


<p>setuid でインストールされていない限り、このコマンドは root だけが使えます。setuid の場合、noexec と nosuid マウントフラグを有効にします。ユーザーマウントについて mount プログラムの慣例に従いますが、追加の制約として、ユーザーはマウント前にそのマウントポイントへ chdir() できなければなりません。</p>

<p>smbclient(8) など一部の Samba クライアントツールは、<em>smb.conf</em> のクライアント側設定を反映します。それらとは異なり、mount.cifs は <em>smb.conf</em> を完全に無視します。</p>

#### 設定 {#CONFIGURATION}


<p>cifs VFS の設定変更やデバッグ情報の読み取りには、主に Linux の /proc ファイルシステムを使います。<em>/proc/fs/cifs</em> ディレクトリには、各種設定ファイルと、デバッグ情報や性能統計を表示できる疑似ファイルがあります。最大バッファーサイズやバッファー数など、カーネルの cifs VFS（cifs.ko モジュール）の読み込み時だけ設定できる起動オプションもあります。cifs.ko に対して modinfo を実行すると、モジュールの導入時（デバイスドライバー読み込み時）に渡せるオプションを確認できます。詳細はカーネルの <em>fs/cifs/README</em> を参照してください。動的トレース（trace-cmd）の設定時に有効化できる SMB3 イベントの一覧は、<em>/sys/kernel/debug/tracing/events/cifs/</em> で確認できます。</p>

#### セキュリティー {#SECURITY}


<p>安全性向上のため SMB2.1以降（最新の方言 SMB3.1.1 を含む）を推奨し、マウント時に SMB1 は既定では要求されなくなっています。CIFS（SMB1、vers=1.0）などの古い方言は、安全性が大幅に劣ります。modprobe cifs disable_legacy_dialects=y で CIFS（SMB1）の使用を無効にできます。</p>

#### 不具合 {#BUGS}


<p>CIFS URL 仕様によるマウントは、現在サポートしていません。</p>

<p>資格情報ファイルでは、先頭に空白のあるユーザー名やパスワードを扱えません。</p>

<p>不具合報告に対しては、まず最新版を試すよう案内されるのが一般的です。先に試し、報告には関連ソフトウェアのバージョンを必ず含めてください。最低限、mount.cifs（mount.cifs <code>-V</code> で確認）、カーネル（<em>/proc/version</em> を参照）、接続しようとするサーバーの種類を記載します。</p>
